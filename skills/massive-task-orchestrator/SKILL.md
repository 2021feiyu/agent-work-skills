# 极大体量任务协调框架

> **上位关系**：本 skill 是 **XL 级专项编排手段**，不替代任务级的流程与裁决。
>
> 本 skill 在两台机器上都会用到，**上位文档按所在机器取其一**，不要混用：
>
> - **体系 A · 五阶段 + 四道门**：上位文档《任务执行规程》——另有轻/重两级判定、三角色（指令执行 / 项目闭环 / 方法沉淀），上位依据 `CONSTITUTION.md` 第四、十一章。
> - **体系 B · 八步 + 三闸门**：上位文档《任务执行框架》——**八步** + G0/G1/G2 三道闸门 + 任务卡/一页规划/验收矩阵三工件。
> - 两套上位文档**不必同名同构**：判为 XL 时**叠加使用**——先用上位文档定"做成什么样 + 验收标准"，再用本 skill 编排 DAG 与多 Agent 波次。
>
> **本机（当前这台电脑）用的是体系 B**：`task-execution-framework` skill 即其载体。

> 处理那些「一口气做不完」的复杂任务——涉及 5+ 个文件、10+ 处修改、需要跨系统同步的工程级变更。
> 核心方法论：**将目标转化为带依赖的 DAG，按波次并行执行，独立验证每一轮输出。**

## 0 适用边界与编排层级

### 0.1 何时激活本框架

| 特征 | 说明 |
|:---|:---|
| 多文件联动 | 修改涉及 3+ 个文件，且文件间有依赖/引用关系 |
| 跨系统同步 | 代码 + 配置 + 技能 + 自动化脚本需同步更新 |
| 多方向并行 | 问题本身可以分解为多个独立的「方向」或「模块」 |
| 步骤复杂 | 单 Agent 容易丢步骤、重复造轮子或遗漏依赖 |
| 质量要求高 | 需要系统性审查、跨文件验证、AST/语法检查 |

**不适用**：单一文件修改、简单查询、独立小任务。

### 0.2 编排层级选型（先判断复杂度，再选编排深度）

**不是所有任务都需要完整 DAG。** 开工前先对号入座：

| 场景 | 复杂度 | 核心动作 |
|:---|:---|:---|
| **Prompt 增强** | 低 | 单 Agent 优化 prompt，不拆分不组队 |
| **Skill 复用** | 低 | 搜索已有 Skill → 直接调用，不组建团队 |
| **计划 + 评审** | 中（**默认**） | 出计划 → 按宿主审批规则执行 → Review 验收 |
| **Lead-Member** | 高 | 主理人协调分配，Member 并行执行，独立验证 |
| **复合编排** | 极高 | 动态组合上述场景，按阶段切换策略 |

**复合编排示例**（某量化交易系统 v3.0 重构实战）：Phase 1-2 走「计划+评审」，Phase 3 走「Lead-Member 并行」，Phase 4 走「独立审查 + 修复」。

### 0.3 与 `long-task-executor` 的分工（先判断，别选错）

| 问题 | 走哪个 |
|---|---|
| 任务在**一次会话内**就能做完，只是改动量大 | **本技能**（DAG + 波次 + 多 Agent） |
| 任务**跨会话**，用户**批量下发多条指令**、中途不反馈、事后统一验收 | `long-task-executor`（跨会话门控 · 台账 · 质检 · 优化 · 结项） |
| 长程任务的**某一个阶段**需要大规模并行改造 | `long-task-executor` 为主，**调用本技能**做该阶段编排 |

两者是**"某一阶段的编排手段" vs "长程任务全程协议"**的关系。判据只看一条：**会不会跨越会话边界、用户是否中途不反馈**——会，就是长程协议；不会，就是本技能。

## 1 核心工作流（5 阶段）

执行一个极大体量任务，**严格按以下阶段推进**。每个阶段输出可验证的工件。

### 1.1 Phase 1：全面拆解与 DAG 建模

**目标**：将模糊需求转化为带依赖关系的任务 DAG（有向无环图）。

**操作**：

1. 完整阅读所有相关文件和上下文
2. 识别独立「方向」或「模块」，每个方向标注：目标、涉及文件、改动量、依赖
3. 输出 **方向 × 文件冲突矩阵**，标记文件级写冲突
4. 构建 DAG：节点 = 子任务，边 = 输入输出依赖。同一依赖层级的任务组成一个**波次（Wave）**

**产出**：DAG 图 + 方向×文件冲突矩阵 + 波次清单。

### 1.2 Phase 2：编写任务列表 + 波次规划

**目标**：将 DAG 转化为可执行的 Task 列表，标注并行边界。

**操作**：

1. 用 `TaskCreate` 创建任务，按波次分组
2. 每个任务含：做什么、验收标准、依赖、预估复杂度
3. 同波次任务可并行派发（**无文件冲突**）
4. 给每个 Agent 明确范围和**禁止触碰的文件清单**
5. **硬性约束**：并行 Agent ≤ 5 个；单个 Agent ≤ 7 个编辑项

**反模式**：一次性给单个 Agent 10+ 个编辑项 → 大概率超时。

**产出**：结构化任务列表（波次 × Agent 分配表）。

### 1.3 Phase 3：多 Agent 波次执行

**目标**：按波次并行派发，Agent 间通过**工件（文件）**间接通信。

**波次结构**：

```
Wave 1: [Agent A: 文件X] ∥ [Agent B: 文件Y] ∥ [Agent C: 新建文件Z]
        ↓ 全部完成后
Wave 2: [Agent D: 文件M(依赖X+Y)] ∥ [Agent E: 配置N(依赖Z)]
        ↓ 全部完成后
Wave 3: [Agent F: 跨文件集成验证]
```

**每个 Agent 的 Prompt 清单**（缺一不可）：

- [ ] 文件路径和行号（**绝对路径**）
- [ ] 具体修改描述（精确到函数/变量名）
- [ ] 验收条件（语法检查 / import / 功能测试）
- [ ] 禁止触碰的文件列表
- [ ] 「完成」的明确定义
- [ ] 约束：控制在 5-7 个 Edit 以内

**Agent 间通信 —— 文件契约模式**：一个 Agent 的产出写入文件 → 下一个 Agent 读取该文件。**不使用内存消息传递**以避免上下文漂移。关键输出用 Schema 定义预期结构。

**Agent 失败处理三阶梯**：

1. **sendMessage 继续**：超时 ≠ 白做，检查已完成进度，精准补做
2. **局部修复（GraSP 原语）**：
   - `Rebind`：修正 Agent 的错误输入参数后重试
   - `Substitute`：换一个 Agent 完成同类任务
   - `Bypass`：当前产出已满足下游需求时跳过
3. **主理人接手**：P2 级批量清理、死代码标注等低风险重复性工作

**防无限循环规则**：

- 每个 Agent 设置轮次上限（`max_turns ≤ 30`）
- 任一 Agent **连续失败 2 次 → 主理人介入**，而非继续 retry
- 使用**布尔退出门**：Agent 不能声明「完成」，直到目标工件通过验证

### 1.4 Phase 4：独立验证（验证者独立于实现者）

**目标**：确保所有修改自洽、无遗漏、无回归。

**三阶段验证顺序**：

1. **语法验证**：`py_compile` / `tsc` / AST check
2. **导入验证**：跨文件 import 兼容性、函数签名匹配
3. **逻辑验证**：历史残留检查（旧版本号/废弃字段/旧函数名 grep）、逻辑冲突检查

**关键防御**：

- 审查 Agent 与修复 Agent **永远分离** —— 实现者不审查自己的代码
- 使用布尔退出门：如 `grep -c "v2\.[0-9]" *.py` 必须返回 0 才算版本号清理完成
- 验证报告含：通过/失败 + 待修复项 + **每项的精确行号**

### 1.5 Phase 5：集成收口

**目标**：所有关联配置同步，系统完全一致。

**操作**：

1. 更新所有依赖此系统的配置、技能文档、自动化脚本
2. 更新项目记忆文件（`MEMORY.md` / `YYYY-MM-DD.md`）
3. 检查所有交叉引用的一致性（版本号、文件名、路径、函数名）
4. 清理临时团队和 Agent

**产出**：最终交付报告 + 变更清单。

## 2 铁律与失败模式

> 本表由原「避坑指南」与「战术集」两节合并而成 —— 两者描述的其实是**同一批规则**（一个用叙述、一个用反模式对照），合并后消除重复并加上分级。

**分级口径**：
- **P0** = 违反会导致改动丢失或错误级联 —— **硬约束，不可协商**
- **P1** = 违反会导致执行失败或资源浪费 —— **强约束**
- **P2** = 违反会降低效率或质量 —— 建议

| 级别 | 反模式 | 后果 | 正确做法 |
|:---:|:---|:---|:---|
| **P0** | 多 Agent 共享写入空间 | 并行写入冲突，改动互相覆盖 | **单写者规则**：同一文件同时只有 1 个写入者。多 Agent 需改同一文件 → 拆成串行波次，前一个完全完成后才启动下一个。主理人亲自改文件前，先确认没有任何 Agent 在操作该文件 |
| **P0** | 无验证门的 Agent 交接 | 上游错误级联放大 | Schema 验证 + **文件契约**；一个波次**全部完成**后才进入下一波次 |
| **P1** | 实现者自我评估 | 假通过 | 实现 Agent 与审查 Agent **必须分离**（独立双 Agent 验证）+ 布尔退出门 |
| **P1** | Agent 承担 8+ 编辑项 | 大概率超时 | 拆分为 ≤7 个编辑项，或分波次。**5-7 个最稳定** |
| **P1** | 一次性上 10 个 Agent | 协调成本爆炸 | **从 2 个 Agent 起步**验证流程，再扩展到 4-5 个（硬上限 5 个） |
| **P1** | 无迭代上限 | 无限循环 | `max_turns ≤ 30` + 布尔退出门；Agent 接近上限时自动总结交回 |
| **P1** | 连续失败仍无限 retry | 资源浪费 | 任一 Agent **连续失败 2 次 → 主理人介入**，不再 retry |
| **P2** | 静态角色分配不调整 | 质量退化无法应对 | 按波次**动态重新分配** |
| **P2** | 纯内存上下文跨长会话 | 上下文漂移 | **活规范文件**持久化；关键规范跨上下文窗口持久 |
| **P2** | 依赖口头传递 | 信息丢失 | 每阶段产出**可验证工件**（DAG 图 / 任务表 / 验证报告） |
| **P2** | 路由用 LLM 兜底 | 慢且不稳定 | 路由决策**优先规则匹配**（关键字 / 文件匹配），降级时才用 LLM 路由 |

**另外两条与表格并列的执行纪律**：

- **超时 ≠ 工作白费**：Agent 超时后用 `sendMessage` 继续即可 —— Agent 保留已完成部分的上下文，只需精准补做
- **Skill 能力回退链**：本地扫描 → skill 搜索 → 通用 subagent → 主线程降级

## 3 角色与术语

| 术语 | 含义 |
|:---|:---|
| **主理人**（Leader / 主控 Agent） | 负责 Phase 1 拆解、Phase 2 规划、Phase 5 收口，以及失败时的介入决策 |
| **Member Agent** | 在波次内并行执行的子 Agent，每个只负责自己范围内的文件 |
| **波次**（Wave） | 同一依赖层级、可并行、彼此**无文件冲突**的任务组 |
| **文件契约** | Agent 间的通信方式：上游产出写入文件 → 下游读取该文件（不用内存消息传递） |
| **布尔退出门** | 客观可判定的完成条件（如 `grep -c` 返回 0），Agent 不能凭自述声明「完成」 |
| **GraSP 原语** | 失败局部修复的三招：`Rebind`（修正输入重试）/ `Substitute`（换 Agent）/ `Bypass`（跳过） |
| **活规范** | 写入文件的长期规范，跨上下文窗口持久化 |

## 4 实战案例

本框架首次实战用于**某量化交易系统 v3.0 重构**（5 个方向 × 6 个文件 × 42 处修改）：

| 阶段 | 实际操作 | 并行度 |
|:---|:---|:---:|
| Phase 1 | 读全部代码 → 识别 5 优化方向 → 输出冲突矩阵 | 1（主理人） |
| Phase 2 | 6 个 Task 创建 → 标注依赖 → 波次规划 | 1（主理人） |
| Phase 3 Wave 1 | 3 Agent 并行（三个互不引用的模块，无文件冲突） | 3 |
| Phase 3 Wave 2 | 主理人补完 2 个超时 Agent 的 P2 收尾 | 1 |
| Phase 4 Wave 1 | 4 审查 Agent 并行（分文件审查，无冲突）→ 发现 42 个问题 | 4 |
| Phase 4 Wave 2 | 4 修复 Agent 并行（技能 + 脚本 + prompt + db，文件隔离） | 4 |
| Phase 5 | 更新 2 个 automation prompt + skill + `MEMORY.md` | 1（主理人） |

**总成果**：6 文件 42 处修改，12 个 Agent 参与，3 个 Agent 超时后恢复，全部 AST 通过。

**这一案例的三条可复用判据**：

1. **Wave 1 只放"互不引用"的模块**——冲突矩阵为空时才允许并行，否则串行；
2. **超时不等于失败**——3 个超时 Agent 全部靠 `sendMessage` 接回，重跑成本远高于续跑；
3. **审查与修复必须分成两个 Wave**——同 Wave 内既审查又修复，等于让实现者给自己打分。
