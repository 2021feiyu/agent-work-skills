# 长报告生产

**一句话**：把"一份十万字级长报告"做成可复现的流水线——多 Agent 分片并行写作，主线程统一重排与裁决，全程不留"没人拍板"的空白。

> **本技能自身的维护**：它已按"执行时间线"重排过一次（旧版是 7 节逐轮追加的补丁式结构）。**若后续累计追加 ≥3 次、或又出现"同一主题散落多处"，先按 `skill-maintenance` 做一次结构重构，再继续追加**——不要让它重新退化成一摞补丁。

---

## 0 适用边界

| 适用 | 不适用 |
|------|--------|
| 十万字级长报告（行业全景、技术栈梳理、专题研究） | 短问答、单点资料查询 |
| 对既有报告"加章节／改单片后重拼"的迭代 | PPT／Excel／H5 看板（走对应专用技能） |
| 需要把多个 Agent 的分头产出合并为口径一致的文档 | 单文件、单次可完成的小任务 |

> **与 `long-task-executor` 的关系**：本技能提供**长报告的生产流水线**；
> 若该报告是**批量下发、中途零反馈**的长程任务中的一条，则其**执行协议**
> （门控 / 台账 / 质检 / 优化）走 `long-task-executor`——本技能 §8 的协作协议是它的**来源之一**，
> **两者不并行执行**。**单次即可完成的长报告，直接用本技能，不必走长程协议。**

## 1 总览：四阶段 + 四份伴随文档

```
启动 ──▶ 结构设计 ──▶ 派发与写作 ──▶ 合并重排 ──▶ 审计裁决 ──▶ 终验交付
  │         │             │             │           │            │
  └─────────┴─────────────┴─────────────┴───────────┴────────────┘
             协作协议与待决策台账：贯穿全程，从第 0 天启用
```

**四份伴随文档**（缺一份都会在后面付出代价）：

| 文档 | 作用 | 何时建 |
|------|------|--------|
| `FRAMEWORK.md` | 框架地图 + 迭代协议 + 口径基线 + 版本记录 | 结构设计时 |
| `待决策事项台账.md` | 记录"提出但未获回复"的问题与默认判断 | **第 0 天**（见 §8.2） |
| `审计待修复清单.md` | 审计发现的问题台账（分级 + 处理方向 + 进度） | 审计开始时 |
| `parts/` 分片目录 | 迭代单元（可单片重写后重拼） | 结构设计时 |

对应**三件交付物**：最终报告.md ｜ 框架文档 ｜ 待决策台账。

## 1.5 四道闸门内嵌（**技能流程不得绕开**）

> **来源与坐标系**：本节判据来自公司侧《数字员工共同宪法》第四章「五阶段四道门」（2026-09-20 起）。
> 本机没有那部宪法，对应物是 `task-execution-framework` 的 **8 步 + G0/G1/G2 三闸门**；
> 下表把四道门挂到本机闸门上。**判据本身与治理体系无关，可直接用；门号沿用原文，便于对照。**
>
> 原则不变：**任何技能的执行流程必须内嵌这些门，技能不得自建一套流程与之并行。**

| 门 | 本机对应 | 本技能中的位置 | 判据 | 不通过 |
|---|---|---|---|---|
| **门 1 理解门** | **G0** | §2 启动之前 | **五问齐全**（是什么／给谁看／怎么算过／**哪一类**／**规模中枢与上限**）＋ **强制对齐判据已核**（六条） | 回澄清；两轮不清则上报 |
| **门 2 可执行门** | **G1** | §3 结构设计出口 | **产物结构已定（五项）** ＋ 每步可答"输入 / 输出 / 用什么" | **不得进入派发** |
| **门 3 执行门** | 执行阶段 | §4 派发与写作中 | 无静默跳过；报错三段式（自修 ≤2 次）；异常即时记录 | 停止上报 |
| **门 4 交付门** | **G2** | §7 终验之前 | **五类校验**：① **需求符合性** ② 口径 ③ 交叉 ④ 异常 ⑤ 可复现 | 退回修正；**严禁先交付再补校验** |
| **归档** | 落盘纪律 | §7.2 之后 | 另存新版本、不覆盖；日志当次写；未闭环进索引 | — |

> **门 1 的"哪一类"是本技能必须问清的第一件事。** 本技能承接 ≥3 万字成稿，
> 但**必须先定是「整合型」还是「论证型」**——两族骨架完全不同：
> **整合型**＝分类体系 ＋ 检索导航 ＋ 索引三件（术语表 / 图表目录 / 主体索引）；
> **论证型**＝论点 → 支撑 → 证据 ＋ SCQA 开篇 ＋ 执行摘要强制。
> **形态错了，写 25 万字也救不回来**（2026-09-20 事故：25 万字、211 个题注、
> 却按"叙事递进"排，且 8 个一级标题全部叫「模块N」）。
>
> **门 4 的"需求符合性"是首类**：对照门 1 留痕逐项核对
> "是什么 / 给谁看 / 怎么算过 / 哪一类 / 规模中枢"。**它回答的是"这是他要的吗"。**

## 2 启动（一次性设置）

### 2.1 前置确认（用 AskUserQuestion，不可省）
- **主题边界**：通用全景 vs 绑定单一主体
- **对标结构**：有参照报告→读它并沿用骨架；无→按内容性质自建
- **用途档位**：个人阅读 / 内部汇报 / 对外分享（影响措辞、署名、以及"事实／判断分离"的写法）

### 2.2 目录与脚本骨架（先建，再开工）

```
<project>/
├── FRAMEWORK.md          # 框架地图 + 迭代协议 + 口径基线 + 版本记录
├── 待决策事项台账.md      # 见 §8.2
├── 审计待修复清单.md      # 见 §6
├── assemble.py           # 按 ORDER 拼接分片
├── parts/                # 分片（迭代单元）
│   ├── p00_front.md
│   ├── p01_...md
│   └── p99_appendix.md
└── parts_v1/             # 结构变更前的备份
```

`assemble.py` 要点：ORDER **显式列表**（不靠文件名字典序）、分片间插 `---`、缺片即报错中止、输出字数与字节统计。

> **为什么用 Python 而不是 shell**：Windows 下 bash 环境常出现 PATH 损坏（`ls`/`head`/`dirname` 找不到），Python 直接调用更稳。凡涉及多行文本或含反引号的替换，写成 `.py` 文件执行，**不要用 `python -c` 内联**——bash 会把反引号当命令替换。

## 3 结构设计（本阶段不写字数预算）

主线程亲自完成，产出四样东西。

### 3.1 分片与命名

`p00_front` / `p01..pNN` / `p99_appendix`；一章可拆多片（如 `p08` + `p08b`）。分片即迭代单元——P1 改一处、P2 重写一片、P3 改结构。

> ⚠️ **硬纪律：生产语汇不得进入交付物**（§1.5 门 1 之落地，2026-09-20 事故直接教训）
>
> **分片名 / 模块名 / `part` /「专项深化」「（上）（下）」等生产语汇，
> 不得出现在报告的一级标题、目录与正文自指里。**
> 报告对读者说话时，**只用内容层语汇（章 / 节）**。
>
> **事故实录**：25 万字报告的 8 个一级标题全部叫「模块1」～「模块7」，
> 20 个目录条目标题里 19 个带生产语汇——
> 读者打开目录看到的是**任务分解表**，不是报告目录。
> **分片名是给人（和迭代）看的，章节名是给读者看的，两者不得混用。**

### 3.2 五要素模板（每节缺一不可）

```
正文 → 术语速释（> **术语速释 · X**：…）→ 表格或图 → 案例（> **举例**：…）
     → 关键认知（> **关键认知**：…）+ 数据来源说明
```

四类标注块全文统一，便于机械裁剪（同一份底稿可裁成个人阅读／内部汇报／对外分享三版）。

### 3.3 展示方式分配
哪一节用**表**（结构化对比）、哪一节用**图**（关系／流程／时间轴）、哪一节必须配**案例**（抽象概念）。分配由"该节的理解成本"决定，不平均分布。

### 3.4 逻辑递进设计
- 每章开头写**挂接句**（"上一章讲 X，本章转向 Y"）
- 章末写**前向指引**（"这一层的结论将在第 N 章用到"）
- **避免同名不同义**：同一概念只在一处定义，其余章引用

### 3.5 核心原则：为什么不设字数上限

**长内容的难点不是长度，而是结构。** 不设字数预算，也不在超额后压缩——那只会把时间花在删减上，而不是让读者读懂。

正确的做法是补结构：合并同类项、把叙述压进表格说明、删重复判断块——**但不删信息**。

> 教训来源：曾给每章设 6000—7500 字上限，导致作者反复压缩、来回返工（压完又被要求加回），往返三轮。而最终成稿时，最重要的一章自然长到了其他章的 2.7 倍——**那个长度是内容决定的，不是配额决定的**。

## 4 派发与写作

### 4.1 可读性设计（与专业度同向，不是降门槛）

长报告要"专业度不降、理解门槛下降"，只有两条路：

**① 具象化案例**——术语照旧保留，在抽象概念首次出现处插入 80—200 字的具体例子。

- **强制规则**：每个类比必须 ① 显式标注为类比（"可以这样理解：""一个具体例子："）② **追加一句边界说明**（该类比在何处失效）
- 好例：讲 MoE 用"大医院不必所有科室同时开工，只叫相关科室会诊"——**边界说明补的是"MoE 降的是算力，不降显存"**，因为未激活的专家仍常驻显存。这一句挡住了选卡时的常见算错。
- 反面教材：用大白话替换术语——那是降专业度，不是降门槛

**② 可视化**——用 Mermaid 嵌在 Markdown 内（保持单一交付物，不与正文分裂）。

- 图型对应：分层图（结构）、传导图（层间关系）、时间轴（演进）、漏斗图（逐级折损）、矩阵（二维分类）
- 优先画**理解成本最高**的位置，不要均匀分布
- **时间轴类图有额外价值**：把多个并列对象画在同一时间尺上，**时点矛盾会立刻显形**——这是逐条比对表格做不到的

### 4.2 Agent 派发规程

- 每分片 1 个 general-purpose，`run_in_background=true`
- prompt **必须自包含**（Agent 看不到主对话）：范围 + 标题层级模板 + 输出**绝对路径** + 五要素模板 + 案例规范 + 数据纪律 + **已确立的关键口径清单**
- **不设字数限制**。若要收束，收在结构而非删信息
- 派发后**不轮询、不纠结任务列表**：以分片文件落盘为真实验收标准

### 4.3 编号不由 Agent 决定

Agent 只需按本节顺序**临时编号**，**主线程在合并时统一重排全篇编号**（章节号、节号、表号、图号）。

> 教训：曾让三节各自编号，结果 17-7 至 17-9 被两组表同时占用；也曾事前提醒过作者，但提醒赶不上成稿节奏。**结论：编号协调不能靠提醒，只能靠合并时统一重排。**

## 5 合并与统一重排

1. header／footer 由主线程写（统管全文口径）
2. `assemble.py` 拼接
3. **编号统一重排在此步一次性完成**
4. 重排后立即扫描四类连带项：章号 / 节号 / **表号** / 交叉引用

> **表号是最高频漂移项**，多 Agent 分头写作时几乎必出问题（实测出现：8 张表全无编号 / 编号起点错误 / 跳号 / 半角空格）。重排后必须**逐片核对"表 X-"的出现次数与连续性**，不能只看表格总数。

## 6 分片审计与分级裁决

合并后派 3—5 路 Agent **分片审计，只读不改**，各报四类：

| 类别 | 具体查什么 |
|------|-----------|
| **跨章一致性** | 同一数据／术语／概念在不同章表述不一致（含分母、时点、单位） |
| **编号残留** | 必须扫**表格单元格内**的编号与跨章引用——正文行首之外最易漏 |
| **逻辑递进断裂** | 章间衔接、概念前置（读者被导向尚未展开的章节）、章节内容重复 |
| **可视化建议** | 哪里该配图、画什么 |

主线程汇总去重后**分级裁决**：

| 级别 | 判据 | 处理 |
|------|------|------|
| **P0 数值直冲** | 同一事实被记成不同刻度 | **必改**；冲突项一律**补限定语**，不简单二选一 |
| **P1 结构断裂** | 导航缺失、章节重复、时间窗互相矛盾 | 必改 |
| **P2 口径差异** | 分母不同、单位混用、归类错误 | 择要 |
| **P3 可读性** | 术语未释、概念前置、重复陈述 | 择要 |

> **P0 的处理原则（重要）**：两条互相矛盾的表述**常常各自都对**，只是基准不同。典型如"头部模型之间差距在拉大"vs"已进入统计噪声区间"——前者指同代模型间的分化，后者指已饱和公开基准上的差距。**正确做法是各自补写"在什么基准上"，而不是删掉一条。**

> **结构变更的连带修复**（P3 级）：分片改名、标题与节号、表号、交叉引用四类必须同步。**迁移脚本极易遗漏表格单元格内的编号**（实测遗漏 38 处，读者照旧号会查到别的章去）→ 变更后必做全分片扫描 `\d\.\d\.\d` 与 `\d\.\d` 引用。

## 7 终验与交付

### 7.1 终验清单（不得跳过）
- 编号连续（章节号 / 节号 / **表号**）
- 题注体例统一（`**表 X-Y　标题**` + 空行 + 表格；全书用**全角空格**）
- 术语首现顺序与术语表声明一致
- 交叉引用双向成对
- **需求符合性**（v1.4 新增，**回答"这是他要的吗"**）：与门 1 留痕逐项一致——是什么 / 给谁看 / 怎么算过 / 哪一类 / 规模中枢
- **目录与正文标题一一对应**（v1.4 新增）：目录须覆盖全部层级标题（含各章小结），不得漏章
- **索引三件齐备**（整合型）：术语表 / 图表目录 / 主体索引
- **双验落盘**：旧文本残留 = 0 **且** 新文本逐项落位 ≥ 1（只查残留不够）
  > **扫描范围必须排除「变更记录」节**——该节为说明"改了什么"**必须出现旧术语**，
  > 不排除会 100% 误报（实测 8/8 全是这种元引用，正文残留为零）。
  > 报警先定归属，再决定改文档还是改脚本。

### 7.2 交付物与其自证要求

| 交付物 | 内容 |
|--------|------|
| **最终报告.md** | present_files 呈现 |
| **框架文档** | 框架地图 / 迭代协议 / 口径基线 / 版本记录 |
| **待决策事项台账** | 见 §8.2，**交付时必须明确告知其存在** |

### 7.3 报告末尾的「文档状态与待决事项」

报告末尾**必须附一节**（如"附录 E"），包含六项：
1. 各章完成度 2. **引用前需核对的数据** 3. 尚未修复的内部不一致 4. **待确认的编辑决策** 5. 可视化进度 6. 一句话总结

> 第 2 项尤其重要：**凡口径有分歧的数据，要在此说明"该数字在不同章按什么口径呈现"**，让引用者知道边界在哪。

## 8 协作协议（贯穿全程）

### 8.1 三条失效模式与结构防线

当用户采用**一次性投放多步任务、中途不校验、只看终局**的模式时（常见于批量任务队列、一人团队 + 数字员工），它把裁决权、上报义务、一致性维护三件事全部转移给了执行者。**执行者必须自带协议。**

| 失效模式 | 表现 | 结构防线（不依赖任何人的警觉） |
|---------|------|---------------------------|
| **自行拍板** | 歧义处默默选一个方案，不报告 | 交付物含**「待确认清单」置于最前**；凡自行判断必须显式标出 |
| **静默降级** | 遇阻降低标准继续产出，不报告 | 交付物含**「执行记录」+「不做清单」** |
| **口径漂移** | 多子任务各自表述，互相矛盾 | **先定口径基线**，后续分片全部引用 |

**关键认识**：这三种失效的共同特征是**不产生任何信号**——输出看起来完整、读起来通顺。因此防线**不能设在"读完检查一遍"，只能设在"产物结构上过不去"**。

### 8.2 待决策事项台账（第 0 天就要建）

**为什么必须建**：批量模式下，执行者的每一次提问都**不会得到即时回复**。若只把问题留在对话里，等于丢失——用户终局验收时无从对账，结果是**执行者默默替用户做了决定**。

**做法**：项目根目录建 `待决策事项台账.md`，**每当出现以下情况立即记入**（不等终局）：
- 主动提出的问题（无论是否已按默认方案执行）
- 因信息不足而自行作出的判断
- 发现但未处理的结构性问题

**格式**（三类分列）：

| 编号 | 问题 | 我的建议／实际做法 | 影响范围 | 状态 |
|------|------|------------------|---------|------|
| **D-01** | 编辑决策（已执行待确认） | 建议怎么做／已怎么做 | 第 X 章 | 已执行 |
| **D-06** | 技术判断（含待执行项） | … | 第 X 章 | 待执行 |
| **S-01** | 可选建议（不阻塞交付） | 做了更好，不做也不影响 | — | 未执行 |

**三条硬性要求**：
1. **必须编号**（D-01／S-01）——用户终局验收时精力有限，编号让"确认／否决"变成几个字符，**极大降低决策成本**
2. **交付时必须明确告知该文档存在**，并说明三种处理方式：一次性批准（"按建议全部执行"）／逐条裁决（按编号回复）／只挑要紧的
3. **在交付物末尾附摘要版**（如报告的「附录 E」）——台账是工作文件，摘要是随交付物走的

**附带收益**：台账天然成为**下一次任务的输入**——已确认的决策沉淀为约定，被否的决策说明偏好，未执行的项直接进入下一轮待办。

> **判断标准**：如果一份交付物里**没有任何"待确认项"**，通常不是因为没有歧义，而是因为执行者把歧义都自己消化了——**这恰恰是最需要警惕的情况**。

### 8.3 五条自查动作

1. **凡自行作出的判断，必须在交付物中显式列出**（对应 §7.3）
2. **交付后不得再改文件**——需修改须重新报告并重跑复检
3. **共享口径先定基线**——多分片共享同一批数据时，先投放"口径定义"任务或写入第一个分片供其余引用
4. **不设字数上限**（见 §3.5）
5. **不依赖"人能发现"**——验收条件写成可核对的形式；检查动作尽量转成产物的结构（清单、记录、附录）

## 9 失败模式对照表（按发生阶段归类）

| 阶段 | 失败模式 | 对策 |
|------|---------|------|
| **写作中** | Agent prompt 缺五要素模板 → 风格漂移、整片返工 | §4.2 必备要素清单 |
| **写作中** | Agent 交付后**仍自行改写**（压缩、补表、改结构）→ 复检结论失效 | 复检结论**绑定文件版本**；对分片动手前先核对 mtime，确认作者已停止写入 |
| **写作中** | 同一文件并行编辑／写入 → 静默覆盖 | **同文件必须串行提交**；每轮改完立即核验落盘 |
| **写作中** | 不同 Agent 对同一指标搜到不同数值 | 审计阶段建"跨章一致性核对表"，统一或显式并列口径 |
| **写作中** | 同一术语被两个分片各自定义 | 先做**术语口径交叉验证**（比通读快）：理想状态是"只在最合适的那章定义，其余引用" |
| **合并时** | 表号漂移（无编号／起点错／跳号／半角空格） | §5 逐片核对出现次数与连续性 |
| **结构变更** | 迁移脚本遗漏**表格单元格内**的编号 | §6 全分片扫描 `\d\.\d\.\d` 与 `\d\.\d` 引用 |
| **术语表** | 声明"按首次出现顺序"却没做到 | 要么真做到，要么改口"按报告结构排列" |
| **全程** | 数据纪律失守 | 见 §10 |

## 10 数据纪律（硬约束，非建议）

- 事实标来源与年份；推演研判用 `> **推演**：`／`> **研判**：` 单独成块，**写明前提假设**
- 查不到权威口径 → 区间表述 + 标注"行业普遍参考值"
- 口径冲突**必须并列，禁止相加或择一**（如实测的"数据中心耗电 Gartner 约 565 TWh vs IEA >1000 TWh"）
- **严禁编造精确数字、虚构机构报告名或政策文号**
- **政策／法规类信息单独加倍小心**：文件名、文号、发布日、施行日逐条核实，并**标注核实状态**（已核实／部分核实／待补），宁可留空也不凭印象写

> 政策类信息的做法参考：某项目附录逐条核实 30 条政策文本，明确标注"已核实 20／部分核实 3／待补 7"，无一条凭印象编写；并因此发现三处跨章时点不一致（发布月、批准日 vs 公布日）——**这类错误单看一章发现不了，只有逐条核实才会暴露。**

## 11 外部理论依据（写方法论时可引用，均需注明来源）

| 理论／案例 | 核心主张 | 对本场景的用法 |
|-----------|---------|--------------|
| **契约式设计**（Design by Contract） | 前置条件 / 后置条件 / 不变式 | 验收条件应前置且可核对，把"完成"从判断变成核对 |
| **任务式指挥**（Auftragstaktik） | 只给意图与边界，不给步骤 | 授权深度由"意图是否被理解 + 边界是否清晰"决定 |
| **丰田安灯绳两级响应** | 一般问题留痕继续，严重问题停线 | 上报门槛必须低，否则无人上报 |
| **poka-yoke（防错）** | 让错误在物理上无法发生，而非提醒人别犯错 | 防线设在"产物过不去"，不设在"人记得查" |
| **ETTO 原则**（Hollnagel） | 人在时间压力下**系统性**牺牲彻底性，这是常态非失误 | 任何依赖"用户自觉中途检查"的设计注定失败 |
| **Urbach 2014**（NEJM，安大略省 101 家医院、约 21.5 万例） | 强制推行 WHO 手术安全清单后，死亡率与并发症率**无显著改善** | **检查单文件可复制、仪式不可复制 → 不存在通用模板，只有机制** |

> 最后一条是**反面证据**，直接否定"照模板填就能用好 AI"的说法。凡写任务设计类内容，应引用它以避免给出伪通用方案。
