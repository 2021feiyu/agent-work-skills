# 技能维护与重构

**一句话**：skill 会死于"打补丁"。这个技能教的是——**什么时候该停止追加，改做整体重构**，以及重构怎么做才不丢经验。

---

## 1 问题：补丁式演进的必然结局

skill 的自然演进方式就是打补丁：每遇到新情况，在末尾追加一节。这本身是**正确的**——经验要及时沉淀，不该攒着。但它的累积后果是结构性的：

| 累积损伤 | 表现 |
|---------|------|
| **顺序错乱** | 章节目录变成"发现顺序"而非"使用顺序"。最晚补的那节常常应该排在最前面 |
| **主题散落** | 同一主题因不同轮次从不同角度补充，散落在 2—3 处，且措辞不一 |
| **份量失衡** | 新补的章节比早期章节详细得多，早期的重要规则被埋在末尾 |
| **要靠"另见"维持一致** | 出现"详见 §X"「同上」这类内部引用，说明本应合并的内容被拆开了 |
| **分类退化** | 出现"其他""补充""注意事项"这类兜底章节——它是结构失效的信号 |

> **判据**：当你回答"这个 skill 里关于 X 的规则是什么"需要翻三个地方时，就该重构了。

---

## 2 触发信号：什么时候停止追加

满足任一条，就应当考虑重构（而不是继续追加）：

1. **累计追加 ≥ 3 次**，或节数比原设计增长超过 50%
2. **同一主题出现在 ≥ 2 处**，需要靠交叉引用维持一致
3. **出现与旧规则矛盾的表述**（不同轮次定的，没回头改）
4. **新读者（或隔一段时间的自己）不知道从哪读起**
5. **出现兜底章节**（"其他""杂项""补充说明"）
6. **章节标题的风格开始不统一**（有的用动词、有的用名词，因为出自不同轮次）

> 反过来，**只追加了 1—2 次、且新增内容自然归位**时，继续追加就好——不要为重构而重构。

---

## 3 重构方法：五步

### 第零步：先备份，再分片构建（安全网）

**重构是有风险的操作** —— 重排会打乱所有交叉引用，重写会误删经验。**必须先建立两道安全网，再动第一行。**

**第一道：时间戳快照**

```bash
D="<skill 目录>"; mkdir -p "$D/versions"
cp "$D/SKILL.md" "$D/versions/SKILL.$(date +%Y%m%d-%H%M%S).md"
```

- 放在 skill 目录下的 `versions/` 子目录 —— 与 skill **同生共死**，不会因换电脑、清缓存、重装而丢
- **带时间戳**，允许多次重构各自留痕；不做覆盖式「上一版」（那会把中间几代重构记录抹掉）
- **不主动删旧版** —— 旧版本身就是「这个 skill 怎么长成现在这样」的记录，且不占运行成本

**第二道：分片构建，延迟覆盖**

不要把新版直接写进 `SKILL.md`，而是：

```
1. 在 .build/ 下按新骨架的章节写成多个分片（part00.md … partNN.md）
2. cat 组装成 .build/SKILL.new.md
3. 跑校验脚本（见第四步）
4. ★ 校验全绿后，才 cp 覆盖 SKILL.md
5. 删掉 .build/
```

这样在整个重构过程中，**原 `SKILL.md` 始终完好无损**（第 1—3 步只读不改），任何一步出错都可以无成本重来。

> 附带好处：分片天然对应新骨架的章节，写的过程本身就在检验「这一节是不是该放在这个位置」。
>
> ⚠️ 收尾务必删除 `.build/` —— 留给下次的应该是 `SKILL.md` + `versions/`，不是一堆半成品分片。

### 第一步：抽取「使用顺序」，而非沿用「发现顺序」

问一个问题：**执行者从零开始做这件事，第一步需要看什么？**

按他实际会查阅的顺序重排，而不是按你当初发现的顺序。

> **实例**：某长报告生产 skill 从 7 节（原则／流程／坑／规范／脚本／协作／台账）重排为 12 节（适用边界／总览／启动／结构设计／派发与写作／合并重排／审计裁决／终验交付／协作协议／失败模式／数据纪律／理论依据）。
> 关键调整有三处：① **协作协议从"流程之后"移到"贯穿全程"**——它必须第 0 天启用，放在末尾等于教人晚做；② 失败模式列表从"按 ROI 排序"改为**"按发生阶段归类"**——读者才知道在哪个阶段防哪个坑；③ 脚本骨架从倒数第二节**前移到"启动"**——读者开工前就需要它。

### 第二步：内容二次嵌合（不是搬运）

重排只是骨架，真正的价值在嵌合：

| 动作 | 做什么 |
|------|--------|
| **合并同类项** | 同一主题散落各处的内容归到一处 |
| **消解重复** | 重复表述只留一份，其余改为指向；**优先保留更具体的那个版本** |
| **升级层级** | 把并列的补丁（A、B、C 三节）提炼为有层次的框架（一个总则 + 三种情形） |
| **补齐缺环** | 重构时往往会发现某个环节**本来就没写**（因为当初没遇到这种情况） |
| **删除失效项** | 已被更好做法取代的旧规则要删，不要"为新旧并存"留后门 |

> **小心"经验损失"**：并入时容易被顺手删掉的，恰恰是**那些看起来琐碎但踩过坑的细节**（如"Windows 下 bash 环境可能 PATH 损坏"）。判据是：**如果这条删了，将来有人会重新踩一遍吗？** 会，就留。

### 第三步：检查份量均衡

打补丁会让新章节比旧章节详细。重构后要检查：

- 早期的重要规则是否被埋在末尾（把它提到该在的位置）
- 新增内容是否喧宾夺主（若是，考虑拆为独立 skill 而非塞进这个）
- 是否存在"过长的单节"（超过全文 40% 的章节，考虑拆分或降级为子节）

### 第四步：验证可用性

- **按新结构走一遍**：模拟一次完整使用，看是否有断裂（读者会在某步找不到所需）
- **检查交叉引用**：所有"见 §X"是否仍指向正确位置
- **检查上下文依赖**：某些规则脱离原位置后是否失去前提（重构最易犯的错）

**辅助工具：九项自动校验**（人工走查会漏，尤其交叉引用）

重排章节编号后**必然**产生悬空引用——靠人眼查 50 处以上引用几乎不可能。

★ **不要在每个 skill 里内嵌一份脚本副本**，统一调用维护好的单一实现：

```bash
python "~/.workbuddy/skills/.skill-check.py" "<目标 skill>/SKILL.md"
```

| # | 检查 | 抓什么 |
|---|---|---|
| **⓪** | **frontmatter 可解析性** | **name/description 非空、YAML 未写坏** ← 加载层第一道门，最容易被漏 |
| ① | 代码围栏偶数配对 | 分片拼装最常见的破坏 |
| ② | 围栏块内出现编号标题 | 围栏配对错位的信号 |
| ③ | U+FFFD 乱码 | 编码损坏 |

| ⑤ | `§X.Y` 引用指向真实节号 | **最核心**，把目检变成确定性判定 |
| ⑦ | 重复二级标题 | 同名两节 = 主题散落的硬证据 |
| ⑧ | 外部 skill 路径引用有效性 | 硬依赖缺失判 FAIL；写明「可选」的算**软引用**，只提示不阻断 |

> **⓪ 为什么必须单独有**：它的故障形态极其隐蔽且后果最重。实战案例——某 skill 的 YAML 键
> 退化成正文标题（`## name: …description:`）、块标量指示符 `>-` 残留、frontmatter 从未闭合，
> 结果 **description 为空 → 该 skill 装了但永远无法被自动唤起**；而①—⑨九项结构检查一项都没报，
> 因为它读的是正文，而问题在正文之前。
> **建议把 ⓪ 放在全库体检的第一步**：结构再好的 skill，加载不进来也等于零。

**脚本精度纪律（2026-09-20 全库首扫踩坑）**：第一次跑全库 52 个 skill，报警 **50 个**，其中真问题只有 1—2 个。**报警数超过 5 个就说明规则有假阳性，先修脚本、再修文档**——否则真信号会被噪声淹没，你会开始无视它。

已识别的假阳性类型（脚本里都已排除，改脚本时别改回去）：

| 假阳性 | 为什么不是问题 | 排除方式 |
|---|---|---|
| `## 工作流程` 出现在 ```markdown 模板里 | 那是示范骨架，不是正文章节 | 从 ④/④b/⑦ 中排除围栏内行号 |
| `## 5 个 category`、`## 5 个编写技巧` | 「数字+量词」是计数标题，不是章节号 | 数字后紧跟量词则跳过 |
| `## 1.1 Baseline` 被截成节号「1」 | 小节号在 H2 层 | 数字后跟 `.数字` 则不算章节号 |
| `## 3.2 Workflow` vs `## 5.2 Workflow` | 不同章下的同名小节，正常 | 判重 key 保留完整编号 |
| `## Workflow` vs `## 3.2 Workflow` | 前者是章、后者是升格的小节 | 同上 |
| `按 X 技能中的 §1.2` | 指向别的文档，不是本文档节号 | 跨文档引用整条链排除 |
| GitHub URL 里的 `/tree/`、`/blob/` | URL 段，不是本地 skill 名 | ⑧ 只认 `.workbuddy/skills/` 前缀 |

| 假阳性 | 为什么不是问题 | 排除方式 |
|---|---|---|
| 行尾空白 27—204 处（9 个 skill 全中） | **CRLF 文件**按 `\n` 分割后每行尾部残留 `\r` | 分割前先归一化 `\r\n` → `\n` |
| 围栏内出现 `## 总体判断` | 那是**输出模板**里的示范标题（无编号） | ② 收窄为只报「**带编号**的标题」 |
| 章节号不连续（实际含 0） | 原文允许**从 0 或 1 起**连续 | 期望值取 `range(nums[0], ...)`，不写死 1 起 |
| 引用不存在的 skill 目录「AI」 | `~/.workbuddy/skills/AI图片生成无水印/` 是**输出示例** | 带 `~` 的路径视为软引用跳过；正则支持中文名，避免截断 |
| 连续空行（3 行） | 只在**文件末尾**，非正文结构问题 | 统计前剔除首尾空白行 |
| `「三-附②」` 被判为补丁痕迹 | 那是**被举例引用**的编号 | 匹配前剥离引号内内容 |
| 代码示例被判为「同规则跨节重复」 | 同一段代码在不同章节各给一次是**正常示范** | 匹配前把围栏内行置空 |
| 「补丁」二字被判为补丁标记 | 它是**主题词**（「skill 会死于打补丁」），讲此现象的文档会自我命中 | 标记正则不含裸词，只认 `-附②`／`（新增）`／`v2.1新增` 等形态 |
| 「附录 A·编码约定速查」被判为兜底章节 | 它**有明确主题**，是合法附录 | 兜底只认真正的兜底词（其他/杂项/补充说明），不含 附录/附注/附表 |
| 章节少时单节占比偏高被判份量失衡 | 3 章的文件单节必然占比高 | 单节占比只在**章节数 ≥5** 时判，阈值提到 60% |
| 「附录 A/B/C/D」「场景A/B/C」被判主题散落 | 那是**族名**重复，不是主题散落 | 被 ≥3 章节共享的词视为族名；且只用中文词做判据 |

**两轮合计：59 处报警 → 真信号 3 处（命中率约 5%）。**

**由此得到一条边界**：脚本只能覆盖**部分结构症状**（占比失衡、补丁标记、文本重复）；**「语义散落」——同一规则换个措辞写在两处——脚本抓不到**，必须读原文。
**二者不可互相替代**：脚本负责把 35 个文件筛成 4 个，语义审查负责判这 4 个（以及脚本看不见的另外 5 个）到底要不要动。

**还有一条更重要的提醒**：本节这段纪律**原本就写在 §3 里**，而 2026-09-20 的审查者（另一个 Agent）在没有重读本节的情况下，用两轮试错**独立重新发现**了它。
教训不是"纪律缺失"，而是 —— **写校验脚本之前，先完整读一遍本节**。纪律写在文档里不等于会被执行。

```python
# ⑤ 的核心：先把跨文档引用摘掉，再查本文档引用
RE_XDOC = r'[A-Za-z0-9_`-]+\s*§\d+(?:\.\d+)*(?:-[A-Za-z])?'          # `other-skill` §4.2
RE_XDOC += r'(?:\s*[、,，/+和与]\s*§\d+(?:\.\d+)*(?:-[A-Za-z])?)*'     # 链尾：同一文档的后续节号
RE_EXTDOC_LINE = re.compile(r'\.md\b|SKILL\.md|skills[/\\]|技能|其中|中的')
kept = ['' if RE_EXTDOC_LINE.search(l) else l for l in lines]         # 提及别文档的整行摘掉
self_text = re.sub(RE_XDOC, '', '\n'.join(kept))
refs = set(re.findall(r'§(\d+(?:\.\d+)*)', self_text))
```

## 4 三条不重构的理由（除非满足其一，否则不要重写）

1. **临近交付**——重构有风险，先追加，同时记一条"待重构"标记
2. **只追加了 1—2 次**——结构还清楚，继续追加
3. **新内容与旧结构天然契合**——它自然归到了正确位置，说明结构设计是好的

---

## 5 跨技能审计：单文档重构抓不到的那一层

§1—§4 讲的是**一个 skill 内部**的结构损伤。但还有一类问题需要**同时读两个文件**才能发现：

> 两个各自都很健康的 skill，放在一起会互相打架。

一个 skill 内部的校验脚本永远不会报出这种冲突——它只看得到自己。实战中最典型的两种：
两个金融数据 skill 各自写明「**禁止使用其他 skill 获取同类数据**」（模型同时加载会拿到互斥指令）；
四个联网检索 skill 都在做同一件事，却**两两零提及**。

### 什么时候该做

任一条成立：

- 用户反映「模型选错入口了」——同一句话命中了不该命中的 skill
- 某个域里堆了 3 个以上职责相近的 skill
- 新装了 skill，怀疑与已有的撞车
- 刚做完一轮单文档重构（此时文档内部已干净，剩下的问题只可能在文档之间）

### 两条补充判据

| 判据 | 检出条件 | 为什么危险 |
|---|---|---|
| **排他声明冲突** | 两个 skill 都用「必须 / 严禁 / 禁止 / 唯一 / 权威 / 不得」排除同类来源 | **互斥指令**。模型同时加载两者时行为不可预测，且没有任何一侧告诉它谁优先 |
| **交叉引用缺失** | 两个 skill 会在同一句话上相遇，但没有任何一侧写明出口 | 「该用谁」变成**涌现行为**而非设计：靠 description 关键词自己去竞争 |

### 怎么检测（关键：别按「词」匹配）

**描述措辞的相似度会骗人，不能作判据。** 关键词重合度最高的一对，可能恰恰是边界**最清楚**的一对——
因为它们把「2D 走谁 / 3D 走谁」写进了描述里，重合度是路由写清楚的**结果**，不是病因。

三种信号，可信度递减：

1. **章节骨架的实质重合**（最可信）——剥掉编号与样板标题（`工作流程` / `Gotchas` / `输出规范` /
   `使用方式`）后逐条比对 H2/H3。**若两个文档对应段落连举的例子都一样，那是同一份文档写了两遍。**
2. **交叉引用的有无**——某 skill 名是否出现在另一文档里（见下方陷阱）。
3. **描述层关键词重合度**——只作参考。

**检测 skill 名必须按「引用写法」匹配，绝不能按普通词匹配**——skill 名常与常用词同形：

| 撞车 | 会误报成引用的东西 |
|---|---|
| `pdf` | 文件扩展名 `.pdf`、包名 `pdfkit-py`、CLI 取值 `--from_format pdf` |
| 任意短名 | 斜杠枚举里的取值 `auto / pdf / docx` |

只认这三种写法才算「指向一个 skill」：① 反引号包裹 `` `name` ``；② 后接 `skill` / `技能` / `SKILL.md`；
③ 出现在「路由 / 分工 / 另见」语境。**代码围栏内的用法示例一律不算**（那里出现的名字多是参数取值）。
识别不出来的个例，**人工复核后列白名单**，别为了让脚本干净而放宽规则——放宽会让真阳性一起消失。

### 补充：判据有两种失效模式，别只防一侧（2026-09-20 跨机实测）

本节原文重点警告的是**假阳性**：描述措辞相似，其实边界很清楚。但同一套判据还有**反向的坑**：

| 失效模式 | 表现 | 后果 |
|---|---|---|
| 假阳性（原文已警告） | 措辞相似 → 误判为重叠 | 白做一次合并 |
| **假阴性（原文未覆盖，实测踩到）** | **看起来不像，其实是** | **静默漏报，直到运行时才暴露** |

**实测**：`enterprise-deep-research` 与 `deep-research-report` 都做「研究报告」、触发词高度重叠，
但章节标题**0 个相同**（一个写「适用边界」，一个写「何时启用」）——
骨架字面比对完全抓不到。后果是 AI 执行任务时才发现两者竞争，必须现场裁决。

**关键认知**：本节说的「章节骨架的**实质**重合」指**语义**重合，**不是标题字面重合**。
把「实质」实现成「字面」，就是从规范到代码的偏离 —— 而且会静默失效。

### 补充判据：同域检测（专补假阴性）

用受控词表把 skill 按「域」归类，同域且组内存在**零引用**成员即报。
四条实现纪律，每条都是踩出来的：

| 纪律 | 为什么 |
|---|---|
| **只匹配 description，不匹配章节标题** | 标题是「内容」—— 任何提到「分析」二字的 skill 都会被误判成研究类（首版报出 7 个「研究报告」，无一属实） |
| **只用专有词** | 删掉「研究」「报告」「分析」这类泛词，改判「研究报告」「行业研究」「尽调」等组合词 |
| **只取适用范围段，排除 `Do NOT use`** | 排除项里出现的词会污染判域 —— 实测某 skill 因 `Do NOT use` 提到 PPT/Excel/看板而被归入 3 个错误的域 |
| **必须展开 YAML 块标量 description** | `description: >` 后跟续行；只取第一行会拿到 `>`，整类 skill 被判「无描述」**静默跳过** —— 该缺陷直接导致漏掉那对关键 skill |

输出形如（已实现为 `.skill-overlap.py` 的 ⓪ 段）：

```
【研究报告】deep-research-report、enterprise-deep-research   ✓ 已有互指
【PDF 处理】pdf、pdf-image-text-extractor、pdf-to-faithful-md  ⚠️ 组内零引用
```

### 流程缺口（必须补）

本节把「**新装了 skill，怀疑与已有的撞车**」列为审计触发条件 ——
但**接收／安装新 skill 的流程里没有这一步**。实测安装了 11 个外来 skill，
只做了结构校验与内容信号扫描，**没做同域影响评估**，冲突直接落地。

**要求**：新 skill **安装前**先做同域检测，同域则**必须补路由才能安装**。
放在安装之后，等于让冲突先落地再补救。

**路由补丁的最小形态**：在双方 description 里各加一句
「**Do NOT use** …走 `对方skill`」—— 双向互指才算补全；
单向路由（A→B 而 B 不提 A）仍会让 B 被误命中。

### 处置优先级（按不处理的后果排，不按工作量排）

| 级别 | 情形 | 动作 |
|---|---|---|
| **P0** | 排他声明冲突 | **定优先级，不是合并。** 两条「禁止绕过」不能共存，必须由人拍板谁主谁备 |
| **P0** | frontmatter 损坏 / 文件名错误导致 description 为空 | **先修**——这类 skill 根本没被加载过，谈不上职责重叠 |
| **P1** | 完全包含（A 只是转发壳，或 A ⊂ B） | **合并或删除。** 删 A 之前必须先把 A 的触发词补进 B 的 description，否则丢失触发覆盖 |
| **P2** | 无路由 / 单向路由 | **补路由表。** 工具链不同的不必合并，写明出口即可 |
| **不动** | 职责天然分层，或产出物形态不同 | **保持。** 为整齐而加路由是负收益——要敢于对大部分簇写「不需要动」 |

### 可复用工具

```bash
PY=<受管 python>
# 1) 抽取全库元数据（frontmatter / 章节骨架 / 体量 / 附带资源）→ inventory.json
$PY ~/.workbuddy/skills/.skill-inventory.py
# 2) 跑重叠检测：描述层触发词重合 + 骨架层章节重合 + 同域并排
$PY ~/.workbuddy/skills/.skill-overlap.py > overlap-report.txt
# 3) 逐文档结构校验（§3 第四步的九项检查）
$PY ~/.workbuddy/skills/.skill-check.py <skill>/SKILL.md
```

`每次做完把评分最高的若干对人工复核一遍`——脚本给的是候选，判定必须靠人读原文。

## 6 定期维护建议

- **每个 skill 维护一份"版本记录"**（版本 / 日期 / 变更），便于判断累计追加次数
- **每累计 3—5 次更新，做一次结构审查**（审查 ≠ 重构：看一遍，判断是否需要）
- **重构前先备份**（做法见 §3 第零步），确认新版可用后再谈旧版去留
- **重构后，把"这次为什么重构"写进版本记录**——下次判断时这是最有用的输入
- **每季度做一次跨技能审计**（§5）——单文档重构做得再干净，文档之间的漂移也不会自动消失

## 7 一条判断原则

> **skill 的价值不在于"记得多"，而在于"在正确的时刻能被找到"。**

补丁式演进优化的是"记得多"，重构优化的是"能被找到"。两者都需要——但**缺了后者，前者的收益会随时间递减**：内容越全，索引越乱，越难找到。

推论到文档之间：**两个 skill 各自被找到 ≠ 该被找到的那一个被找到**。这正是 §5 存在的理由。

## 8 与相邻技能的分工

| 场景 | 用哪个 |
|------|--------|
| 新建一个 skill | `skill-builder` |
| 给 skill 追加 1—2 条新规则 | **直接追加**（不必调用本技能） |
| skill 已累计多轮更新、结构混乱 | **本技能**（§1—§4） |
| 多个 skill 职责重叠 / 抢同一触发词 | **本技能**（§5 跨技能审计） |
| 审查某个 skill 的内容质量 | `skill-builder` 的审查功能或 `critical-code-reviewer` |
| 审查 skill 的安全性 | `skills-security-check` |
